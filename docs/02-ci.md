### What I learned along the way

- **`npm ci` vs `npm install`:** `npm ci` installs the *exact* versions in `package-lock.json`, never edits the lockfile, and fails if `package.json` and the lockfile disagree. That's what makes CI builds reproducible. `npm install` is for local development.
- **Cache:** saves downloaded packages between runs. The key is a hash of the lockfile: same lockfile means the cache is reused, changed lockfile means a fresh download. The install step still runs on a cache hit; it's just faster.
- **Linter vs test:** a linter reads the code without running it (static analysis); tests run it and check the behaviour.
- **`needs:`:** jobs run in parallel by default. `needs:` makes a job wait for others *and* skips it if any of them fail.
- **Images don't survive the job.** GitHub-hosted runners are ephemeral: when the job ends the VM is deleted, and the image built on it goes too. To keep an image it has to be pushed to a registry (next step: GHCR).
- **`on:` shows up as `True` in PyYAML.** PyYAML follows YAML 1.1, where `on`/`yes`/`no` are booleans (the "Norway problem"). GitHub reads it correctly; quoting it as `"on":` avoids the ambiguity.
- **`docker build` runs on BuildKit (buildx)** in current Docker, which is why its errors mention `docker buildx build`.

## Workflow-level settings

```yaml
"on":
  push:
    branches: [main]
  pull_request:
    branches: [main]

concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true

permissions:
  contents: read
```

| Setting | Reason |
|---|---|
| `"on"` quoted | `on` is a reserved boolean keyword in YAML 1.1. Quoting it keeps the key as the literal string `"on"` instead of a parser interpreting it as `true`. |
| `concurrency` | A second push to the same branch cancels the run already in progress, instead of two runs racing each other. |
| Top-level `permissions: contents: read` | Least privilege. The default `GITHUB_TOKEN` would otherwise get write access to everything; each job raises only the permission it actually needs (the `images` job adds `packages: write` to push to GHCR). |

## Job 1 — `backend-test`

Runs `pytest` against a real PostgreSQL 16 container, not SQLite or a mock, so CI catches the same issues as [Step 3b](01-docker.md#step-3b--switch-sqlite--postgresql) did locally (overlapping bookings, row locking).

```yaml
services:
  postgres:
    image: postgres:16-alpine
    env:
      POSTGRES_USER: vrcm
      POSTGRES_PASSWORD: vrcm
      POSTGRES_DB: vrcm_test
    ports:
      - 5432:5432
    options: >-
      --health-cmd "pg_isready -U vrcm -d vrcm_test"
      --health-interval 5s
      --health-timeout 3s
      --health-retries 10
```

- `services:` starts a throwaway container alongside the job, torn down when the job ends. No `docker compose` needed in CI.
- The `options:` healthcheck is the same `pg_isready` check used in `docker-compose.yml`. GitHub Actions waits for it before running any step, so `pytest` never races an unready database.
- `defaults.run.working-directory: backend` means every `run:` step in this job executes inside `backend/` without repeating `cd backend`.
- `TEST_DATABASE_URL` is set only on the test step, pointing at `localhost:5432` (the service container's published port). The test fixtures read this variable and point the app at it.

## Job 2 — `frontend-build`

Installs with `npm ci` (exact versions from `package-lock.json`, same reasoning as the Dockerfile in [Step 2](01-docker.md#step-2--containerize-the-frontend-multi-stage-build)), then runs `npm run lint` and `npm run build`. Catches lint errors and build failures — the same two things that would otherwise only surface when building the frontend Docker image.

## Job 3 — `images`

Builds the backend and frontend Docker images, scans them for vulnerabilities, and pushes them to `ghcr.io` — but only once both `backend-test` and `frontend-build` have passed:

```yaml
needs: [backend-test, frontend-build]
strategy:
  fail-fast: false
  matrix:
    service: [backend, frontend]
```

- `needs:` must name the job's **id** (`backend-test`), not its display `name:` (`Backend Test`). Getting this wrong makes the workflow fail validation before anything runs.
- The matrix runs the same steps twice — once per service — instead of duplicating every step for backend and frontend.
- `fail-fast: false` lets the backend image finish scanning even if the frontend image fails, so one bad image doesn't hide the other job's result.

**Build → scan → gate → push, in that order:**

1. **Build** with `docker/build-push-action`, `load: true` (loads the image into the local Docker daemon instead of pushing yet) and `cache-from`/`cache-to: type=gha` (reuses Docker layer cache between workflow runs via GitHub's cache).
2. **Scan** with Trivy, `exit-code: "0"` — reports CRITICAL and HIGH findings in the log but never fails the job. This step exists purely for visibility.
3. **Gate** with a second Trivy step, `severity: CRITICAL` and `exit-code: "1"` — fails the job if any CRITICAL vulnerability is found. `skip-setup-trivy: true` reuses the Trivy binary the first scan already installed instead of downloading it twice.
4. **Push**, only `if: github.event_name == 'push'`. Pull requests build and scan images but never push them to the registry — a PR from a fork shouldn't be able to publish images under this repo's name.

```yaml
run: echo "IMAGE=ghcr.io/${GITHUB_REPOSITORY_OWNER,,}/vrcm-${{ matrix.service }}" >> "$GITHUB_ENV"
```

`${GITHUB_REPOSITORY_OWNER,,}` lowercases the repo owner with bash parameter expansion, because GHCR image names must be all lowercase but a GitHub username/org can contain uppercase letters.

Each image is tagged twice on push: `:<git-sha>` (immutable, traceable to the exact commit) and `:latest` (convenient for `docker pull` without knowing a SHA).

### Pinning actions by commit SHA

Every `uses:` pins a full commit SHA with the version as a trailing comment, e.g.:

```yaml
uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
```

A tag like `@v4` can be moved by the action's maintainer (or an attacker who compromises their account) to point at different code without changing the version number in the workflow file. A commit SHA is immutable — `@3d3c42e...` always runs that exact code. The `# vX.Y.Z` comment exists only so a human reading the file can tell which release it is.

I verified each pin against GitHub's API (`GET /repos/<owner>/<repo>/git/refs/tags/<tag>`) before trusting it — for an annotated tag (like `aquasecurity/trivy-action`'s), the tag ref points at a tag *object*, which has to be dereferenced one more level to reach the actual commit SHA.

## Bugs I hit

| Symptom | Cause | Fix |
|---|---|---|
| `frontend-build` job silently missing from CI | `frontend-build:` was written at column 0 instead of indented 2 spaces under `jobs:`. YAML parsed it as a brand-new top-level key, sibling to `jobs:`, instead of a second job inside it. | Indent it to match `backend-test:`. |
| Same bug again, this time on the `images` job | Same cause: `images:` was pasted in at column 0. | Same fix: indent to column 2. Caught by re-checking with `yaml.safe_load` and inspecting `jobs.keys()` after every edit, not just visually. |
| Would have failed with "job `backend-tests` is not defined" | `needs: [backend-tests, frontend-build]` referenced a job id with a trailing `s`; the real job id (and its `name:` is "Backend Test") is `backend-test`. | Match the `needs:` entries to the actual job keys under `jobs:`, not the display name. |
| Trailing whitespace and no newline at end of file | Pasted content ended mid-line. | Not a functional bug, but cleaned up for a tidy diff. |
| *(Rebuild, step 5)* `jobs.keys()` showed only `backend-test` | Ran the check before saving the file in the editor. | Save, then re-run the check. `git diff` shows what's actually on disk. |
| *(Rebuild, step 6)* `ERROR: docker: 'docker buildx build' requires 1 argument` | A space after the colon in `-t vrcm-backend: ${{ github.sha }}` split the tag into two shell arguments, so Docker saw two build contexts. | Remove the space: `vrcm-backend:${{ github.sha }}`. Found by reading the expanded command on the step's "Run" line in the log. |
| *(Rebuild, step 6)* Frontend job green but nothing was built | While adding `build-image`, the `npm run build` line was accidentally deleted, leaving the frontend "build" step with an empty `run: \|`. An empty step passes, so CI stayed green. | Put `npm run build` back under the build step. **A green check only proves the steps that exist passed. Read the diff, not just the colour.** |

**Lesson:** YAML's structure is defined entirely by whitespace, so a misplaced job key doesn't raise a syntax error — it just reassigns the job to the wrong place in the document, and GitHub Actions either ignores it or rejects the whole workflow depending on where it lands. `python -c "import yaml; print(yaml.safe_load(open('ci.yml'))['jobs'].keys())"` catches this immediately; eyeballing the file does not.
